- Review
	- For Heap Files, two access APIs for accessing data:
		- fetch by `recordld` (`pageld`, `slotld`)
		- scan (starting from some page)
- Q. Wouldn't it be nice if we could look things up by value?
	- i.e. a declarative access API
	- Index!
- **Index**: An index is data structure that enables fast lookup and modification of data entries by search key
	- **Lookup**: may support many different operations
		- Equality, 1-d range, 2-d range
	- **Search Key**: any subset of columns in the relation
		- Do not need to be unique, e.g. first name
	- **Data Entries**: items stored in the index
		- e.g. a pair (`k`, `recordId`)
			- Pointers to records in Heap Files
			- Easy to generalize later
	- **Modification**: want to support fast insert and delete
- Idea #1: [[L7.1 ISAM]]
- Idea #2: [[L7.2 B+ tree]]
- Q. How to build an index on a large table?
	- Can we just call insert repeatedly?
	- Inefficient!
		1. Constantly need to search from root
		2. Leaves and internal nodes mostly half-empty
		3. Modifying random pages brings poor cache efficiency
- [[L7.3 bulk loading of B+ tree]]
- Summary
	- ISAM is a *static* structure
		- Only leaf pages modified; overflow pages needed
		- Overflow chains can degrade performance unless size of data set and data distribution stay constant
	- B+ Tree is a *dynamic* structure
		- Inserts/deletes leave tree height-balanced; log<sub>F</sub>N cost
		- High fanout (F) means depth rarely more than 3 or 4.
		- Almost always better than maintaining a sorted file.
		- Typically, 67% occupancy on average
		- Usually preferable to ISAM; adjusts to growth gracefully.
	- Bulk loading can be much faster than repeated inserts for creating a B+ tree on a large data set.
	- B+ tree widely used because of its versatility
		- One of the most optimized components of a DBMS.
		- Concurrent(并发) Updates
		- In-memory efficiency
