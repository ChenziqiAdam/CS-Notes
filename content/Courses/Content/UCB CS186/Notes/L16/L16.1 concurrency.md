- Concurrent Execution: Multiple transactions are allowed to run concurrently in the system.
- Advantages are twofold:
	- Throughput (transactions per second):
		- Increase processor/disk utilization -> more transactions per second (TPS) completed
			- Single core: can use the CPU while another is reading to/writing from the disk
			- Multicore: ideally, scale throughput in the number of processors
	- Latency (response time per transaction):
		- Multiple transactions can run at the same time
		- So one transaction's latency need not be dependent on another unrelated transaction. That's the hope.
-  Example
	- User 1
	```sql
	UPDATE Budget
	SET money = money - 500
	WHERE pid = 1

	UPDATE Budget
	SET money = money + 200
	WHERE pid = 2
	
	UPDATE Budget
	SET money = money + 100
	WHERE pid = 3
	```
	- User 2
	```sql
	SELECT sum(money)
	FROM Budget
	```
	- In this case, the order of execution matters!
	- Also users need to specify what is OK.
- Different Types of Concurrency Problems
	- Inconsistent Reads
		- User 1
		```sql
		INSERT INTO DollarProducts(name, price)
		SELECT pname, price
		FROM Product
		WHERE price <= 0.99
		
		DELETE Product
		WHERE price <= 0.99
		```
		- User 2
		```sql
		SELECT count(*)
		FROM Product
		
		SELECT count(*)
		FROM DollarProducts
		```
	- Lost Update
		- User 1
		```sql
		SELECT count(*)
		FROM Product
		SELECT count(*)
		FROM DollarProducts
		```
		- User 2 (Overwrite)
		```sql
		UPDATE Product
		SET Price = Price *0.6
		WHERE pname = "CoolToy"
		```
	- Dirty Reads
		- User 1
		```sql
		UPDATE Account
		SET amount = 1000000
		WHERE number = "my-account"
		```
		- User 2
		```sql
		SELECT amount
		FROM Account
		WHERE number = "my-account"
		```
		- If User 1's transaction is aborted by the system, User 2 will get a dirty entry.
- Transaction is the solution.
