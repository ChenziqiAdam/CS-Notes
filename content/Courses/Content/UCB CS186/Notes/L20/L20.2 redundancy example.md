- Example: Constraints on Entity Set
	-   Consider relation Hourly_Emps: `Hourly_Emps (ssn, name, lot, rating, wage_per_hr, hrs_per_wk)`
	- We can denote a relation schema by listing its attributes:
		- e.g. `SNLRWH`
		- This is really the set of attributes `{S, N, L, R, W, H}`
	- And we can use relation name to refer to the set of all its attributes
		- e.g. "Hourly_Emps" for SNLRWH
	- Q. What are some FDs on Hourly_Emps?
		- `ssn` is the primary key: S -> SNLRWH
		- `rating` determines `wage_per_hr`: R -> W
		- `lot` determines lot: L -> L ("trivial" dependency)
	![[Pasted image 20250804111732.png]]
	- Problem 1: Update anomaly
		- Q. Can we modify W in only the 1st tuple of SNLRWH?
		- No. Then that tuple will be inconsistent with Smiley and Madayan!
	- Problem 2: Insertion anomaly 
		- Q. What if we want to insert an employee and don't know the hourly wage for his or her rating? (or we get it wrong?)
		- Then you will have to invent a value without reference to established truth!
	- Problem 3: Deletion anomaly
		- Q. If we delete all employees with rating 5, we lose the information about the wage for rating 5!
		- Then we will forget established truth!
- Detecting Redundancy
	- Q: Why is R -> W problematic, but S -> W not?
	- A: R is not a key, so any pair ((8, 10) for example) can appear multiple times. S is a candidate key, so each pair (e.g. (123-22-3666, 10)) is stored exactly once.
- Decomposing a Relation
	- Redundancy can be removed by "chopping" the relation into pieces.
	- FD's are used to drive this process
	- R -> W is causing the problems, so decompose SNLRWH into two tables: one is R -> W and one without R -> W.
