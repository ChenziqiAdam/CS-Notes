- Schema
	`Sailors (sid: integer, sname: text, rating: integer, age: real)`
	`Reserves (sid: integer, bid: integer, day: date, rname: text)`
	- Reserves:
		- Each tuple is 40 bytes long, 100 tuples per page, 1000 pages.
		- Assume there are 100 boats
	- Sailors:
		- Each tuple is 50 bytes long, 80 tuples per page, 500 pages.
		- Assume there are 10 different ratings
	- Assume we have 5 pages (buffers) to use for joins.
- Plan 1: Base line
	```sql
	SELECT S. sname
	FROM Reserves R, Sailors S
	WHERE R.sid=S.sid
	AND R.bid=100
	AND S.rating>5
```
	![[Pasted image 20250715165000.png|200]]
	- Cost: 500+500\*1000 l/Os
		- Scan Sailors (500 lOs)
		- For each page of Sailors, Scan Reserves (1000 lOs)
	- Misses several opportunities:
		- selections could be 'pushed' down
		- no use made of indexes
	- Goal of optimization:
		- Find faster plans that compute the same answer.
- Plan 2&3: Selection Pushdown
	![[Pasted image 20250715165353.png]]
	- The left saves half the scan of sailors when paired with reserves, i.e. 500+250\*1000.
		- Scan Sailors (500 lOs)
		- For each pageful of high-rated Sailors, Scan Reserves (1000 lOs)
	- While the right does not improve better, it pays for scanning reserves.
		- Scan Sailors (500 IOs)
		- For each pageful of high-rated Sailors, Scan Reserves (1000 IOs)
- Plan 4: Join Ordering
	![[Pasted image 20250715165745.png|200]]
	- Cost: 1000+10\*500
		- Scan Reserves (1000 lOs)
		- For each pageful of Reserves for bid 100, Scan Sailors (500 lOs)
- Plan 5: Materializing Inner Loops
	![[Pasted image 20250715170356.png|200]]
	- Cost: 4250
		- Scan Reserves (1000 lOs)
		- Scan Sailors (500 lOs)
		- Materialize Temp table T1 (250 IOs)
		- For each pageful of Reserves for bid 100, Scan T1 (?250 IOs)
- Plan 6: Materializing on original Join order
	![[Pasted image 20250715170514.png|200]]
	- Cost
		- Scan Sailors (500 lOs)
		- Scan Reserves (1000 lOs)
		- Materialize Temp table T1 (10 IOs)
		- For each pageful of high-rated Sailors, Scan T1 (10 IOs)
- Plan 7: sort merge Join
	![[Pasted image 20250715171004.png|200]]
	- Cost: 1000 + 500 + sort reserves(10 + 2\*10) + sort sailors(250 + 3\*2\*250) + merge (10+250) = 3630
		- Scan Reserves (1000)
		- Scan Sailors (500)
		- Sort:
			- Sort high-rated sailors
				- 2 passes for reserves
				- pass 0 = 10 to write, pass 1 = 2\*10 to read/write
			- Sort reservations for boat 100
				- 4 passes for sailors
				- pass 0 = 250 to write, pass 1,2,3 = 2\*250 to read/write
		- Q. How many passes for each sort with log,?
		- Merge (10+250) = 260
- Plan 8: sort merge Join with Materializing on original Join order
	![[Pasted image 20250715171347.png|200]]
	- Cost: 2140
		- Scan Sailors (500)
		- Scan Reserves (1000)
		- Write Temp T1 (10)
		- For each blockful of high-rated sailors, Loop on T1 (63 * 10)
- Plan 9: Projection Cascade & Pushdown
	![[Pasted image 20250715172046.png|200]]
	- To fully utilize 1 buffer and fill in all the reserves on boat 100
	- Cost: 1500
		- Scan Reserves (1000)
		- For each blockful of sids that rented boat 100 (recall Reserve tuple is 40 bytes, assume sid is 4 bytes) Loop on Sailors (1\*500)
- Plan 10: Index
	- Indexes:
		![[Pasted image 20250715172305.png]]
		- `Reserves.bid` clustered
		- `Sailors.sid` unclustered
			- `Column.sid` is a **primary key** for Sailors.
			- <=1 matching tuple, unclustered index on `sid` OK
		- Assume indexes fit in memory
	- Cost: 10 + 1000\*1
		- With clustered index on bid of Reserves, we access how many pages of Reserves?:
			- 100,000/100 = 1000 tuples on 1000/100 = 10 pages.
		- For each Reserves tuple 1000 get matching Sailors tuple (1 IO) (recall: 100 Reserves per page, 1000 pages)
