### Cost Notation

- $[R]$ : the number of pages to store $R$
- $p_{R}$ : number of records per page of $R$
- $|R|$ : the cardinality (number of records) of $R$
- $|R| = p_{R} * [R]$
### Simple Nested Loops Join

- Note: for simplicity we do not present iterator implementations for the join algorithms.
- Example:
	- $[R]$=1000, $p_R$=100, $|R|$ = 100,000
	- $[S]$=500, $p_s$=80, $|S|$ = 40,000
- Case 1
	```
	foreach record r in R do
		foreach record s in S do
		if θ(ri, sj) then add <r, s> to result buffer
	```
	![[Pasted image 20250702164343.png|200]]
	- Cost = $[R]$ + $|R|[S]$ = 4,000,001,000
- Case 2
	```
	foreach record s in S do
		foreach record r in R do
			if θ(ri, sj) then add <r, s> to result buffer
	```
	![[Pasted image 20250702164544.png|200]]
	- Cost = $[S]$ + $|S|[R]$ = 50,000,500
- Order of Join matters!
### Page Nested Loop Join
```
for each rpage in R:
	for each spage in S:
		for each rtuple in rpage:
			for each stuple in spage:
				if join_condition(rtuple, stuple):
					add <rtuple, stuple> to result buffer
```
![[Pasted image 20250702164947.png|200]] -> ![[Pasted image 20250702165002.png|100]]
- Cost = $[R]$ + $[R]*[S]$ = 501,000
- Block (Chunk) Nested Loop Join
```
for each rchunk of B-2 pages of R:
	for each spage of S:
		for all matching tuples in spage and rchunk:
			add <rtuple, stuple> to result buffer
```
![[Pasted image 20250702165332.png|200]]
- Cost = $[R]$ + $[R]/(B-2)*[S]$ = 102
- Much Better! Should set by default
### Index Nested Loop Join
```
foreach tuple r in R do
	foreach tuple s in S where ri == sj do
		add <r, s> to result
```
- Cost = $[R]$ + $|R| *$ cost to find matching S tuples
- If index is 
	- Alt 1: cost to traverse tree from root to leaf. (e.g., 2-4 lOs)
	- For Alt. 2 or 3:
		- Cost to lookup RID(s); typically 2-4 IOs for B+ Tree.
		- Cost to retrieve records from RID(s)
			- Clustered index: 1 I/O per *page of matching S tuples*
			- Unclustered: up to 1 I/O per matching S tuple
- Example
	- Reserves (`sid`: int, `bid`: int, `day`: date, `rname`: string)
		- $[R]$=1000, $p_R$=100, $|R|$ = 100,000
	- Sailors (`sid`: int, `sname`: string, `rating`: int, `age`: real)
		- $[S]$=500, $p_s$=80, $|S|$ = 40,000
		- Index on sid
	- Unclustered Cost(R,S) = $[R]$ + $|R|$ * (Search + HeapAccess)
	- Clustered Cost(R,S): $[R]$ + $IR|$ * (Search) + `distinct_vals(R)` * HeapAccess
	- Unclustered B+-Tree height 2 (3 l/Os from root to leaf):
		- $R \bowtie S$: 1000 + (100,000)\*4 = 401,000
	- Clustered B+-tree height 2 (3 l/Os from root to leaf)
		- $R \bowtie S$: 1000 + (100,000)\*3 + `distinct vals(R)` = 301,000 + X < 100.000
### Sort-Merge Join

- Requires equality predicate: Equi-Joins & Natural Joins
- Two Stages:
	1. Sort tuples in R and S by join key
		- All tuples with same key in consecutive order
	2. Join Pass: Merge-scan the sorted partitions and emit tuples that match
![[Pasted image 20250704170319.png|600]]
- Cost: `Sort R` + `Sort S` + $([R]+[S])$
	- But in worst case, last term could be $[R]*[S]$ (very unlikely!)
		- all of the join values of R and S are the same
		- a.k.a. simple nested loops join
	- Question: How big does the buffer have to be to sort both R and S in two passes each?
		- Suppose buffer B > $\sqrt{\max_{([R], [S])}}$
			- Both R and S can be sorted in 2 passes
			- 4\*1000 + 4\*500 + (1000 + 500) = 7500
- Join & Sort Order
	```sql
		SELECT sid, bid, sname, rname
		FROM R, S
		WHERE R.sid = S.sid
		ORDER BY sid
```
	- Join First, Sort Later
		- Join: $[S] + ([S]/(B-2))*[R]$ = 5,500
		- Sort: $2 * [R]* (1 + log_{B-1} [R]/B)$ = 4000
	- Sort First, Join Later
		- Total = 7500 = 
			- + Sort R: 2\*[R]\*(2) = 4000
			- + Sort S: 2*[S]\*(2) = 2000
			- + R + S = 1500
- Refinement: An important refinement combines last pass of merge-sort with join pass
	- Given enough buffers to sort both relations simultaneously...
	- Do the join during the final merging pass of sort
		- Read R and write out sorted runs (pass 0)
		- Read S and write out sorted runs (pass 0)
		- Merge R-runs and S-runs, while finding R ~ S matches
	- 2-pass Cost = $3*[R] + 3*[S]$ = 3000+1500 = 4500
		- Requires Buffer >= $\sqrt{R}$ + $\sqrt{S}$ = 32 + 23 = 55
### Hash Join
#### Naive In Memory Hash Join

- Requires equality predicate: Works for Equi-Joins & Natural Joins
- Assume R is smaller relation
	- Require R to fit in memory
	- Simple algorithm:
		- Load all R into hash table
		- Scan S and probe R
	- Memory requirements:  R < (B-2) * hash_fill
		- No requirement for the size of S
- $R \bowtie_{sid} S = \cup(\sigma_{hash(sid)}(R) \bowtie_{sid} \sigma_{hash(sid)}(R)$
	- Can decompose into smaller "partial joins"
	- Pick a hash function s.t. $\sigma_{hash(sid)}(R)$ fits in memory!
#### Grace Hash Join

- Requires equality predicate: Equi-Joins & Natural Joins
- Two Stages:
	1. **Partition** tuples from R and S by join key and store on scratch disk
		- all tuples for a given key in same partition
	2. Build & Probe a separate hash table for each partition (like in Naïve Hash)
		- Assume partition of smaller rel. fits in memory (recurse if necessary...)
	![[Pasted image 20250704171742.png]]
```
For Cur in {R, S}
	For page in Cur
		Read page into input buffer
		For tup on page
			Place tup in output buf hashr (tup.joinkey)
			If output buf full then flush to disk partition
	Flush output bufs to disk partitions
For i in [0..(B-1)]
	For page in Ri
		For tup on page
		Build tup into memory hashr (tup.joinkey)
	For page in Si
		Read page into input buffer
		For tup on page
			Probe memory hash, (tup.joinkey) for matches
			Send all matches to output buffer
			Flush output buffer if full
```
![[Pasted image 20250704172925.png]]
![[Pasted image 20250704173250.png]]
- Note:
	- Each key is assigned to one partition
		- e.g., green star keys only in Partition
	- Sensitive to key Skew
		- Fuchsia circle Key
	- Each partition could be on a different disk or even different machine (parallel!)
- Summary
	- Total cost of 2-pass hash join = Partitioning + Matching = (2 + 1)($[R]+[S]$) = 3 * (1000 + 500) = 4500
	- Memory Requirements
		- Build hash table on R with uniform partitioning
			- Partitioning Phase divides R into (B-1) runs of size $[R]$ / (B-1)
			- Matching Phase requires each $[R]$ / (B-1) < (B-2)
			- R < (B-1) (B-2) = $B^2$
		- Note: no constraint on size of S (probing relation)!
	- Naive v.s. Grace
		![[Pasted image 20250704173747.png]]
		- **Naive** Hash Join: requires $[R]$ < B
			- Put all of R in hash table
			- 1/3 the I/O cost of Grace!
		- **Grace** Hash Join: 2-passes for [R] < B?
		- **Hybrid** Hash Join: an algorithm that adapts between the two
			- Tricky to tune
#### Hash Join v.s. Sort-Merge Join

- Sorting pros:
	- Good if input already sorted, or need output sorted
	- Not sensitive to data skew or bad hash functions
- Hashing pros:
	- For join: # passes depends on size of smaller relation
		- e.g. if smaller relation is <B, naive/hybrid hashing is great
	- Good if input already hashed, or need output hashed
