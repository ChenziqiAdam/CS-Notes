- Recall
	- B: The number of data blocks
	- R: Number of records per block
	- D: Average time to read/write disk block
	- F: Average internal node fanout
	- E: Average # data entries per leaf

|                  | Heap File  | Sorted File                 | Clustered Index                     |
| ---------------- | ---------- | --------------------------- | ----------------------------------- |
| Scan all records | B\*D       | B\*D                        | 3/2 \* B\* D                        |
| Equality Search  | 0.5\*B\*D  | (log<sub>2</sub>B)\*D       | log<sub>F</sub>(BR/E)\*D            |
| Range Search     | B\*D       | (log<sub>2</sub>B+pages)\*D | (log<sub>F</sub>(BR/E)+3\*pages)\*D |
| Insert           | 2\*D       | (log<sub>2</sub>B+B)\*D     | (log<sub>F</sub>(BR/E)+3)\*D        |
| Delete           | (B/2+1)\*D | (log<sub>2</sub>B+B)\*D     | (log<sub>F</sub>(BR/E)+3)\*D        |

- Note:
	- Recall assumption from before regarding clustered indexes: heap file pages only 2/3 full, thus for full pages it needs to time 3/2
	- 3: access + leaf file update + heap file update

| Big O Notation   | Heap File | Sorted File         | Clustered Index     |
| ---------------- | --------- | ------------------- | ------------------- |
| Scan all records | O(B)      | O(B)                | O(B)                |
| Equality Search  | O(B)      | O(log<sub>2</sub>B) | O(log<sub>F</sub>B) |
| Range Search     | O(B)      | O(log<sub>2</sub>B) | O(log<sub>F</sub>B) |
| Insert           | O(1)      | O(B)                | O(log<sub>F</sub>B) |
| Delete           | O(B)      | O(B)                | O(log<sub>F</sub>B) |

- Be careful with constant factors
	- Example: Assume you can do 100 sequential I/Os in the time of 1 random 1/0
	- For a particular lookup, is a B+-tree better than a full-table scan?
		- Had better be very "selective"
			- Visit < 1% of pages!
		- Or do mostly sequential 1/0 at leaf level
			- Clustered index
		- Or use SSD
			- SSDs make indexes attractive
			- Especially for read-mostly workloads
