- Page Replacement Terminology Review
	- Q. How will the buffer manager know if a page is "in use"?
		- **Page pin count**
	- Q. If a buffer manager is full, what page should be replaced?
		- **Page Replacement policy**
- Life circle of a page
	- The process when a page is requested
		1. If requested page is not in pool:
			- Choose an un-pinned (pin count = 0) frame for replacement.
			- If frame "dirty", write current page to disk, mark "clean"
			- Read requested page into frame
		2. Pin the page and return its address
		- If requests can be predicted (e.g., sequential scans) pages can be pre-fetched.
	- The process after a page is requested
		1. Requestor of page must:
			- set dirty bit if page was modified
			- unpin the page (preferably soon!)
				- To allow the buffer pool replacement policy lots of latitude to choose which frame
		2. Page in pool may be requested many times
			- a pin count is used
			- To pin a page: pin count +1
			- A page is a candidate for replacement iff pin count is 0 ("unpinned")
		3. CC & recovery may do additional l/Os upon replacement
			- Write Ahead Log protocol
- Page Replacement Policy
	- Page is chose for replacement by a **replacement policy**
		- Least-recently-used (LRU), CLOCK
		- Most-recently-used (MRU)
		- Policy can have big impact on # I/Os
			- Depends on the access pattern
	- LRU Replacement Policy
		- Pinned Frame: not available to replace
		- Track time each frame last unpinned (end of use)
		- Replace the frame which was least recently used
		- Disadvantage: inefficient for CPU (linear)
	- CLOCK policy: simplified PRU
		![[Pasted image 20250625174730.png]]
		- Current frame is pinned
			- Skip
		- Current frame not pinned
			- Reference bits = 1
				- Set reference bits = 0
				- Skip
			- Reference bits = 0
				- Replace
				- Set pinned
				- Set reference bits = 1
	- Q. Is LRU/CLOCK always best?
		- Very common policy: intuitive and simple
		- Works well for repeated accesses to popular page
			- Temporal locality
		- LRU can be costly -> Clock policy is cheap
	- Q. What about repeated scans of big files (common in nested loops)? e.g. 6 frames for 7 pages
		- For LRU, "Sequential Flooding"
			- 0% hit rate, same for CLOCK
		- But for MRU
			- Much better!
			- (B-1)/N hit rate, i.e. 5/7% here
- Q. How to further improve for sequential scan?
	- **Prefetch**: Ask disk space manager for a run of sequential pages
		- Amortize(分摊) random I/O overhead
		- Allow computation while I/O continues in background
			- Disk and CPU are "parallel devices"
- Q. It seems that we need a hybrid of LRU and MRU
	- LRU wins for random access (hot vs. cold)
	- MRU wins for repeated sequential
	- Approach 1: Use DBMS information to hint to buffer managers
		- For big queries: we can predict 1/O patterns from the handful of query processing algorithms (we'll learn shortly)
		- For simple lookups: LRU often does well
	- Approach 2: Fancier stochastic policies, e.g. 2Q
