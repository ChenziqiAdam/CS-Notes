### 1. SLLists
- Q. the IntList in lecture 4 works well, but it is "naked" and hard for the users to use.
	It requires the users to know the references and think recursively.
- **Improvement #1: Rebranding and Culling**
	```Java
	public class IntNode {
		public int item;
		public IntNode next;
		
		public IntNode(int i, IntNode n) {
			item = i;
			next = n;
		}
	}
```
- **Improvement #2: Bureaucracy
	```Java
	public class SLList {
		public IntNode first;

		public SLList(int x) {
			front = new IntNode(x, null);
		}

		public void addFirst(int x) {
			first = new IntNode(x, first);
		}

		public int getFirst() {
			return first.item;
		}
	}
```
	- SLLists vs. IntLists
		```Java
		SLList L = new SLList(15); // IntList L = new IntList(15, null);
		L.addFirst(10); // L = new IntList(L, 10);
		L.addFirst(5); // L = new IntList(L, 5);
		int x = L.getFirst(); // int x = L.first; 
```
		- SLLists are much simpler to use.
		- Users don't need to know references or recursion.
	- SLList class acts as a middle man between users and the raw data structure.
- **Improvement #3: Private
	- Q. users might do something dangerous ignorantly
		```Java
		SLList L = new SLList(15);
		L.addFirst(10);
		L.first.next.next = L.first.next; // The last node is pointing to itself
```
		- Sol: use the `private` keyword to prevent codes in other classes from using members (or constructors) of a class.
	- Why restrict access?
		To hide implementation details from users of the class
		- less for users to understand
		- safe for programmers to change `private` methods (`public` implies that the members will work forever).
	```Java
	public class SLList {
		private IntNode first;
		...
	}
```
- **Improvement #4: Nested Classes**
	Can combine two classes into one file pretty simply
	```Java
	public class SLLists {
		private static class IntNode { // Nested class definition
			public int item;
			public IntNode next;
			public IntNode(int i, IntNode n) {
				item = i;
				next = n;
			}
		}

		private IntNode first; // Instance variables, constructors, and methods of SLLists typically go below nested class definition
		public SLList(int x) {
			front = new IntNode(x, null);
		}
	}
```
	- Why nested classes?
		- Nested classes are useful when a class doesn't stand on its own and is obviously subordinate to another class.
	- `private static class IntNode{}`: 
		- `private`: if other classes should never use the nested class, make it private
		- `static`: if the nested class never uses any instance variables or methods of the outer class, declare it static (never look outwards)
			- Static classes cannot access outer class's instance variables or methods.
			- Results in a minor savings of memory.
- **Improvement #5: Fast `size()` : Caching(缓存)**
	- Q. how to get the size of the SLList?
		- **Recursive method**
		```Java
		private int size(IntNode p) { // Helper Method
			if (p.next == null) {
				return 1;
			}
			return 1 + size(p.next);
		}

		public int size() {
			return size(front);
		}
```
	- Q. how to modify SLList s.t. the execution time of `size()` is always fast, i.e. independent of the size of the list?
		- Sol: maintain a special `size` variable that caches(存贮) the size of the list.
			- ***Caching*: putting aside data to speed up retrieval**
			- **Tanstaafl**: although there ain't no such thing as a free lunch, but spreading the work over each add call is a net win in almost any circumstance.
		```Java
		public class SLList {
			private IntNode first;
			private int size;
			public SLList(int x) {
				front = new IntNode(x, null);
				size = 1;
			}
			
			...
			public void addFirst(int x) {
				first = new IntNode(x, first);
				size += 1;
			}
			
			public int size() {
				return this.size;
			}
		}
```
- **Summery**: Benefits of SLList vs. IntList so far:
	SLList class acts as a middle man between users and the naked recursive data structure. Allow programmers to store meta information about the entire list, e.g. `size`.
	- Fast `size()` method than would have been convenient for IntList
	- User of an SLList never sees the IntList class
		- Simpler to use
		- More deeicient `addFirst()` method
		- Avoid errors (or malfeasance)
### 2. SLLists continued
- **Improvement #6: Representing the Empty List Using a Sentinel**
	- Q. how to represent the empty list?
		When you add last to the empty list, you can NOT go to the `null.next`!
		- One possible solution: add a special case (primitive)
	- **==Special cases are not simple.==**
		To be a good programmer, keep in mind that keep your codes simple.
		- Always restrict the amount of complexity in your code
		- Make solutions general
	- Solution: ***Sentinel Node*** (a special node that always stands at the first)
		- Bottom line(基本原则): for `addLast`, having a sentinel makes it no need for a special case to check `null`
		- `sentinel` is never `null`, and (the sentinel reference) always points to sentinel node
		- Sentinel node's item needs to be some integer, but doesn't matter what value we pick
		- Had to fix constructors and methods to be compatible with sentinel nodes
