- **The worst way to approach programming**:
	- read and (mostly) understand the spec
	- write the entire program
	- compile and fix all compilation errors
	- run and get many errors
	- until correct, repeat randomly:
		- run and get many errors
		- add print statements to zero in on the bug (weak tool but easy to use)
		- make changes to code to try to fix bug
	This workflow is slow and unsafe!
- ==**TTD: Test-Driven Development**==
	- Steps to developing according to *TDD*:
		1. Identify a new feature
		2. Write a unit test for that feature
		3. Run the test. It should fail. (RED)
		4. Write code that passes test. (GREEN)
			- Implementation is certifiably good!
		5. Optional: refactor code to make it faster, cleaner, etc.
		(Interesting perspective: Red-Shirt, Red, Green, Refactor)
		(*TDD* is an extreme departure from the naive workflow.)
- Tools for *TTD*:
	**1. *Unit Tests*:**
	- Idea: write tests for every "unit".
		- JUnit makes this easy!
			`testSort()` <--> `sort()`
			`testFindSmallest()` <--> `findSmallest()`
			`testSwap()` <--> `swap()`
	- Why unit tests?
		1. Build confidence in basic modules
		2. Decrease debugging time
		3. Clarify the task
	- Why not?
		1. Building tests takes time
		2. May provide false confidence
		3. Hard to test units that rely on others
	**2. *Integration Testing*:**
	- Idea: Tests cover many units at once.
		- Not JUnit's focus, but JUnit can do this.
	- Why?
		1. Unit testing is not enough to ensure modules interact properly or that system works as expected.
	- Why not?
		1. Can be tedious to do manually
		2. Can be challenging to automate
		3. Testing at highest level of abstraction may miss subtle or rare errors
