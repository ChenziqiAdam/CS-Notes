- Q. Tests are helpful, but it is really troublesome to write such a long program to test one short program.
	- use `pytest`
- `pytest`: a third-party program that can automatically test one's program
	- `pip install pytest`
	- Example:
		```Python
		from calculator import square

		def test_square_zero():
			assert square(0) == 0
		def test_square_negative():
			assert square(-2) == 4
			
		"""
		The version above is better then the one below, i.e. more detailed
		def test_square():
			assert square(0) == 0
			assert square(-2) == 4
		"""
```
	- <u>run</u>: `pytest test_calculator.py`
		- For `float`, it is hard to guarantee float-point precison one hundred per cent.
	- Q. what if programmers want to test what if the user input a `str`:
		- Example
			```Python
			def test_calculator_str():
				with pytest.raises(TypeError):
					square("cat")
```
	- **Avoid Side Effects**: it is hard to test the output, i.e. `print()`.
		- replace with `return`
		- Example:
			```Python
			def hello(to="world"):
				return f"hello, {to}"

			# The test file
			def test_hello_argument():
				for name in ["Hermione", "Harry", "Ron"]:
					assert hello(name) == f"hello, {name}"
				# This is not good as the test should be simple and plain
			def test_hello_default():
				assert hello() == "hello, world"
```
	- **Always keep the tests simple and plain to read.**
- `pytest` support a folder of tests
	- It is helpful and practical to break tests into different parts s.t. it is easier for the programmer to catch which part is wrong.
	- **`__init__.py`**: always to remember to contain a file named "\_\_init\_\_.py" in the folder 
		- s.t. Python will treat the folder as a whole i.e. a package
	- Example
		```csharp
		mkdit test // Create a folder named test
		code test/test_hello.py // Create a new file in the folder
		code test/__init__.py // Tell python to treat the folder as a whole i.e. a package

		pytest test // Test the whole folder
```
